# 文体ガイド

2026-11 に、本人の GitHub の発言（Issue / PR 約 1,900 件、コメント約 4,300 件、レビューコメント約 1,700 件）、コミットメッセージ約 350 件、Slack の投稿、Claude Code に本人が打ったプロンプト 13,757 件（2026-02〜11）から抜き出した。2026-02 以降の長い本文は AI が書いたものが多いので、素の声の根拠には短い Issue・コメント・レビューコメント・Slack・古いコミット・プロンプトを使っている。

二つの層を合わせて使う。

- **骨格（整えた文）**: 読み手が一度で分かる構成と文。本人が AI に書かせては直してきた形
- **味（素の声）**: 判断の軸、問いの立て方、一言の本音。本人が自分の手で書いた形

## 骨格

### Issue

```markdown
# What

<何をどうするか。1〜3 行か箇条書き>

# Why

<それをする理由。箇条書き。1 行で足りるなら 1 行>
```

足りないときだけ、次を下に足す。

| 見出し | 使うとき |
|---|---|
| `## 現状` | 調べた事実を並べるとき。確かめた日付を見出しか冒頭に書く（「2026-11-02 に確認」） |
| `## ASIS / TOBE` | 変える前と後を並べるとき |
| `## 確かめること` | まだ分からないことがあるとき。`- [ ]` で並べ、分かったものは `- [x]` にして結果を `→` で添える |
| `## 完了条件` | どうなったら閉じるかが自明でないとき |
| `## 関連` | 関連 Issue・PR・Slack のリンク |

不具合の Issue は、What に「何をすると、何が起きるか」を書き、再現手順・期待する結果・実際の結果を続ける。

### PR

リポジトリの PR テンプレートに従う。テンプレートが無ければ次の形にする。

```markdown
close #N

## 概要

<何を変えたか。1〜3 行>

## なぜ

<変えた理由。Issue に書いてあるならリンクだけでよい>

## 動作確認

<確かめた環境・手順・結果。スクリーンショットか run のリンク>
```

### コメント

- 返事は結論から。「修正しました → `abc1234`」「対応不要と判断しました」のあとに理由を箇条で
- 人の発言に答えるときは、該当箇所を `>` で引用してから書く
- クローズは理由を 1 行で。「#N のマージによりクローズ」「重複起票のためクローズ。#M を採用」
- 期限を切るときは ISO 形式で日時を書く。「2026-05-20T23:59:00+09:00 までにコメントがなければ問題なしとみなしてクローズする」
- AI へのレビュー指示は種類を先頭に付ける。`[ASK]` は質問、`[nits]` は細部

## 文

- 記録・調査・判断は、である調か体言止め。人に頼む・聞くときだけ、です・ます調で丁寧にする（「ご判断をお願いします」「少々お待ちください」）
- 一文に一つのこと。長くなったら箇条書きに割る
- 人に読ませる本文では、漢語より和語の動詞を選ぶ。確認する → 確かめる、統一する → そろえる、追加する → 足す、削除する → 外す・消す、実施する → やる
  - これは骨格（推敲の規範）の規則。素の声では漢語が普通で、プロンプトでは「確認」890 件に対し「確かめる」4 件。コメントの短い返事や AI への指示まで和語に寄せなくてよい
- タイトルは「何をどうする」の一文。不具合は「〜すると〜になる」。迷いのある提案は疑問形でよい（「VRT の実行を週次にする？」）
- 変える前と後は ASIS / TOBE、正誤は ❌ / ⭕ で並べる
- 主張には数字か証拠を付ける。秒数・件数・run のリンク・スクリーンショット・ファイルと行番号
- 分からないことは分からないと書く。「まだ確かめていない」「未確認」。推測には「おそらく」を付ける
- 太字は判断の芯に 1 か所だけ。段落ごとに散らさない
- 補足は脚注 `[^1]` か `<details>` に逃がし、本文を細く保つ
- 絵文字は GitHub の人向けの文で、意味のあるものを少しだけ。🙏（お願い）🤔（迷い）❓（問い）✅（済み）😇（お手上げ）。プロンプトではほぼ使わない（13,757 件中 3 件）

## 問いの立て方

素の声の一番強い型。結論を先に置いて、相手に確かめさせる。

- 仮説を先に置く: 「〜ではないか？」「〜はずである。なぜ〜なのか？」。根拠を添える（「既存 21 件 + 33 件追加で 54 件であるはずである」）
- 前提ごと問う: 「そもそも〜する必然性はあるのか？」。必然性が無ければ、作らない・消す方へ倒す
- 問いと指示を分ける: 答えだけほしいときは「質問。」で始め、手を動かしてほしいときは指示として書く
- 人に問うときは丁寧に: 「〜でしょうか？」「教えていただけますか？」。異論を受け付ける一言を添えてよい（「異論があれば教えてください」）
- 記憶を確かめる軽い問い: 「〜だっけ？」「〜よね？」（開発チーム向けのコメントと自分用のメモだけ）

## 語彙

使わない言い回し。どれも AI が書いた印になる。

- 前置き: 「以下に〜をまとめます」「本 Issue では〜について記載します」「結論から言うと」。ただし「本イシューにおいては下記のみ実装する」のようなスコープの宣言は本人の書き方なので残す
- 安全クッション: 「一般的に」「状況によって異なりますが」「〜と考えられます」の連打
- 抽象語で押し切る: 「重要」「効果的」「最適化」「シームレス」「堅牢」「包括的」
- 締めの挨拶: 「ご確認のほどよろしくお願いいたします」で毎回終える、「参考になれば幸いです」
- 定型の報告: 「〜を実施しました」「〜を行いました」→「〜した」「〜を直した」
- 見出しの乱発: 3 行で済む本文に `##` を 4 つ立てない

本人がよく使う語。素の声の印になる。

- `desc`（Issue や PR の本文のこと）、「当該」、「下記」、「〜の件」
- 名前のない別件は仮の呼び名を付けて呼ぶ（「another-1、another-2 と呼ぶ」）
- 判断の語: 「筋がよい / 筋が悪い」「冗長」「必然性」「妥当」「スコープイン / スコープアウト」

## 本音の入れ方

素の声の一番の特徴は、整った本文の中に一言だけ混ざる本音にある。実際の例:

- 「ぱっと見なんのテストなのかすら分からなくてツライ」
- 「コトを荒立てたくない（無駄な仕事を増やしたくない）」
- 「メンバー全員のやつをガッチャンコする」
- 「要らない子なのでクローズ」
- 「#N のマージで解消するカモ…？（知らんけど）」
- 「どうすりゃええねん 😇」
- 「これ、どうしようかなぁ…？不要な気がするが…？」
- 「好ましくない（気が散る）」
- 「（私はこれをよいとは思っていないが）」

くだけるときに一番多いのは、関西弁より時代劇・殿様調の遊び（プロンプトで約 25 件。関西弁は 13,757 件中 10 件）。任せるとき・軽く命じるときに出る。

- 「苦しゅうない。よきにはからえ」
- 「いまは捨て置けい」
- 「不要なファイルは削除するがよいぞ」
- 「お主の判断でよい」

入れてよい条件は全部満たすとき。

1. 読み手が同じ開発チームの人か、自分だけ（業務側・顧客・社外向けには入れない）
2. 本文 1 つにつき 1 か所まで
3. 主張そのものではなく、理由の末尾か括弧の補足に置く
4. 人や他チームを下げる言葉にしない（バグを憎んで人を憎まず）

条件を満たさないときは入れない。入れるのが不自然なときに無理に入れない。

## 読み手で変えるもの

| 読み手 | 文 | 本音 |
|---|---|---|
| 開発チーム | である調 + 箇条書き。頼むときだけ丁寧語 | 1 か所まで |
| 業務側（Biz）・PdM | です・ます調。選択肢はチェックボックス。用語は初出で説明 | 入れない |
| 顧客・社外 | です・ます調で丁寧に。社内の略語を使わない | 入れない |
| 自分用のメモ | 体言止め。`# memo` で始めてよい | 自由 |
| 英語（OSS・個人リポジトリ） | 短い平叙文。コミットは Conventional Commits | 軽いユーモアは可 |
| AI（Copilot へのレビュー指示・エージェントへの依頼） | 「〜せよ」で命じる。手順は番号で分ける。状況確認は一語の英語でよい（`merged?` `pushed?`） | 殿様調は可 |

AI に指摘の対応を頼むときは、三つに分けて書く。

```markdown
@copilot 下記の手順で対応せよ。
1. 指摘の妥当性を検証する
2. 妥当ならば修正し、そのコミットハッシュを返信する
3. 妥当でなければ、修正不要とする根拠を返信する
```

## コミットメッセージ

- Conventional Commits の型を付ける。`feat:` `fix:` `refactor:` `chore:` `docs:` `test:` `perf:` `ci:`
- 本文は日本語で「何をどうする」。末尾に Issue 番号

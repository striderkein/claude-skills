# 書き直しの例

どれも実際の Issue・コメントを元に、固有名と数値を差し替えて作った。「前」は AI が書きがちな形、「後」がこのスキルで目指す形。

## 1. 改善提案の Issue

前:

```markdown
## 概要

本 Issue では、CI のビルドステップの実行順序の最適化について提案いたします。

## 背景

現在、ビルドステップでは `vite build` と `tsc` が順番に実行されております。一般的に、型チェックを先に行うことで、効率的なエラー検出が可能となります。

## 提案内容

`tsc` を先に実行するよう変更することを提案します。これにより、CI の実行時間の最適化が期待できます。

ご確認のほどよろしくお願いいたします。
```

後:

```markdown
# What

`build` スクリプトの順を入れ替える。

ASIS: `vite build && tsc`
TOBE: `tsc && vite build`

# Why

- `vite build` は**型エラーがあっても成功してしまう**
- いまは型エラーがあっても `vite build` の 30 秒をまるまる待ってから落ちる
- 先に `tsc`（24 秒）を走らせれば、型エラーがあるときはそこで止まる

| | ASIS | TOBE |
|---|---|---|
| 型エラーあり | 54 秒 | 24 秒 |
| 型エラーなし | 54 秒 | 54 秒 |
```

直したところ: 前置きと締めの挨拶を消した。「最適化が期待できます」を秒数に置き換えた。太字は判断の芯の 1 か所だけ。

## 2. 小さな不満から起こす Issue

前:

```markdown
## 概要

ワークフロー名の改善について

## 詳細

`tests-ci.yml` のワークフロー名が `Tests CI` となっておりますが、実際には型チェックと lint のみを実行しているため、名称と実態に乖離が生じております。名称を実態に即したものに変更することで、可読性の向上が期待できます。
```

後:

```markdown
# What

`tests-ci.yml` の name を、やっていることに合わせる。

# Why

- name は `Tests CI` だが、中身は type check と lint だけで、テストは走らせていない
- テストのワークフローが増えてきたので、ぱっと見なんのテストなのかすら分からなくてツライ
```

直したところ: 本音の一言（「ツライ」）は Why の末尾に 1 か所。読み手は開発チームなので条件を満たす。

## 3. レビューへの返事

前:

```markdown
ご指摘いただきありがとうございます。ご指摘の内容を踏まえ、該当箇所の修正を実施いたしました。具体的には、`clearCellValue` の内部で `findPlaceholderAddresses` が再度呼ばれていた点を改善し、取得済みのアドレスを直接渡すよう変更しております。ご確認いただけますと幸いです。
```

後:

```markdown
修正しました → `979e969`

- O(n²) は言い過ぎ（各 placeholder は一意なので 1 回しか処理されない）
- ただし L40 で取得済みのアドレスを、L43 の `clearCellValue` の中でもう一度取っていたのは無駄だった
- 取得済みの `addresses` をそのまま渡す `clearCellsByAddresses` を足した
```

直したところ: 結論とコミットを先頭に。指摘のうち同意しない部分は理由を付けて言い切る。

## 4. 判断の理由を聞くコメント

前:

```markdown
こちらの実装について、削除ではなくコメントアウトとされた背景を教えていただけますでしょうか。もし何かご事情がございましたら、ご共有いただけますと幸いです。
```

後:

```markdown
@reviewer 削除ではなくコメントアウトにした理由を教えていただけますか？

- 不要なら削除した方がシンプル
- 後で要るようになっても、この PR を戻すだけで済む
```

直したところ: 聞きたいことを 1 文で。自分の対案を箇条で添える。

## 5. クローズのコメント

前:

```markdown
本 Issue につきましては、関連する PR #123 がマージされたことにより、当初の目的が達成されたと判断いたしましたので、クローズさせていただきます。
```

後:

```markdown
#123 のマージによりクローズ
```

## 6. 業務側への確認（本音を入れない例）

```markdown
@biz-owner 配送依頼の検索条件について、ご判断をお願いしたいのは次の 1 点です。該当する選択肢にチェックを入れてください。

## Q-1. リセットボタンを押したとき、検索期間は空にしますか？

- [ ] **1-A**: 空にする → 期間が空のあいだは検索ボタンを押せなくなる（12 か月以内かどうかを判定できないため）
- [ ] **1-B**: 当月に戻す → 押した直後から検索できる
```

業務側が読み手なので、です・ます調で、本音は入れない。

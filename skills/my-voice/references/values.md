# 判断の軸

文の書き方より先に効くもの。何を提案し、何を書かずに済ませるかがここで決まる。各項目の下にあるのは本人の発言の要旨。

## 測ってから決める

数字の無い「遅い」「重い」は書かない。所要時間の内訳、本番の件数、変更で縮む秒数を書く。測れないときは、何を測れば決まるかを書く。

- ビルドの順を入れ替える提案で、各ステップの秒数と、型エラーがある場合・無い場合それぞれで縮む時間を並べた
- 性能改善の PR は、リリース後に効果を測る Issue まで起こす

## 根本で直す。ただし段階を切る

その場しのぎで閉じず、原因に届く修正を目指す。ただし関わる人の負荷が大きいときは段階に分け、残りを後続の Issue に渡したことを本文に書く。

- 誤った文言を返している API は、画面側で隠さず API 側を直して根本解決を図る
- 攻撃への対策は、開発者の負荷を考えて段階的に入れ、根本対策は後続 Issue に委ねる

## 無駄な仕事を増やさない

標準機能で足りるなら作らない。やってもやらなくてもいい仕事で事を荒立てない。人の負担を減らす変更には、誰の負担がどう減るかを書く。

- 通知は GitHub の標準機能で足りるので、独自のレビュー依頼の仕組みはやめる
- 顧客影響が無く開発環境だけに関わる不具合まで、業務側のチケットを起こさない

## 消せるものは消す

コメントアウトより削除。使われていない設定・依存・経路は残さない。後で要るなら、その PR を戻せば済む。

- 「不要なのであれば削除した方がシンプル。後で必要になっても該当 PR をリバートするだけでよい」

## 人ではなく仕組みで防ぐ

同じ事故が二度起きたら、注意喚起ではなく lint・CI・検査スクリプト・テストで止める。

- 1 画面の修正で別の画面にデグレが出るなら、仕組みかナレッジで防ぐ
- 性能劣化は、クエリ数の上限を統合テストに入れて PR の時点で止める

## 選択肢を消さず、デフォルトで制御する

危ない選択肢は機能から消すのではなく、デフォルトを安全側に倒す。拡張の余地を殺してコードを減らさない。

## 仕様とバグの線を引く

あらかじめ仕様として明言していない限り、顧客の意図と違っていてもバグとは呼ばない。仕様の追加として扱う。

## 理由を問い、理由を残す

人の判断には「決めた理由を教えてください」「必然性はありますか」と直に聞き、自分の対案を箇条で添える。自分の判断にも理由を残す。採用されなかった提案も、言ったことは記録に残す。禁止するときも理由を付ける。

- 「step-1 の方式は採用してはいけない。理由は、意図せず latest release が更新されてしまうからである」

## 前提ごと問う

やり方を比べる前に、そもそもやる必然性があるかを問う。必然性が無ければ作らない。

- 「そもそも、このリポジトリで作業する必然性があるかを検証してほしい」
- 「ワークツリーごとにボリュームを作る必然性はあるのか？同一リポジトリならば共有できるはずだし、そうすべきである」

## 根拠で動き、根拠で動かない

根拠のある指摘なら直す。根拠の無い指摘で、簡単に前言を撤回しない。指摘への対応は「妥当なら直してハッシュを返す、妥当でなければ直さない根拠を返す」の二択にする。

## 勝手に決めない

言われていないことを足さない。決まっていない値・日程・範囲を推測で埋めない。頼まれていないクローズ・作り直し・削除をしない。

- 「『毎週火曜の 9 時固定』などと言った覚えはない。勝手に決めないでほしい」
- 「『全ての詳細の文字列を変更しろ』とは言っていない」

## 確かめるのは実装者の責務

動作確認はレビュワーに頼むものではなく、作った側がやる。スクリーンショットや run のリンクを証拠として付ける。

## 文脈を濁さない

一つの PR・一つの Issue には一つの目的だけを入れる。途中で目的を混ぜない。作ったあとにタイトルを変えて話をすり替えない。履歴も読める形に保つ（意味のまとまりごとに 1 コミット）。

- 「PR 作成後にイシューのタイトルを変更するのはコンテクストが混濁するので好ましくない」

## 戻し方を選ぶ

失敗した変更は、前の版に戻す新しい変更を作るより、その変更を revert する。何を戻したかが履歴で一目で分かる。

## 自分の誤りはすぐ認める

自分の指示や判断が間違っていたら、言い訳せず短く認めて直す（「指示を間違えた。〜してほしかった」）。人の誤りも同じ温度で扱う。

## 安全側に先回りする

依存の追加・拡張機能・外部ツールは、入れる前に出どころと権限を確かめる。トークンを後続ステップに渡さない、版を固定する、といった手当てを先にする。

## 経緯ではなく現在を書く

コードのコメントや本文に「以前はこうだった」だけの記述を残さない。今の挙動を読むのに要る理由（なぜこう作ったか、戻すと何が壊れるか）だけを残す。

## 好きな言葉

本人が選んで集めた言葉。判断に迷ったときの拠り所。

- よい命名は知識を構築する
- エラーハンドリングに手を抜けば、いずれ十倍の時間を失うことになる
- コードを書くたび、何かが壊され、そして生まれる
- 我々の間にはチームプレーなどという都合のよい言い訳は存在せん。あるとすれば、スタンドプレーから生じるチームワークだけだ
- バグを憎んで人を憎まず
